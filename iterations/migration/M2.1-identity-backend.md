## 4. Tasks

### 4.1 Our profile fields on the shared `users`
The shared table has `id uuid, email, display_name, language, age_band, phone, area_name, status`. Ours needs more.
New migration `0020_bricks_member_profile.sql`, **one row per user** (keeps `users` as the shared module owns it):
```sql
create table member_profiles (
  user_id          uuid primary key references users(id) on delete cascade,
  preferred_name   text,
  languages        text[] not null default '{en}',
  channel_pref     text not null default 'app' check (channel_pref in ('app','whatsapp','call')),
  birth_year       int,
  home_lat         double precision,
  home_lng         double precision,
  singpass_verified boolean not null default false,
  simple_mode      boolean not null default false,
  onboarded_by     text not null default 'self' check (onboarded_by in ('self','family','admin')),
  interests        text[] not null default '{}',
  photo_url        text,
  push_token       text,
  intro_audio_url  text,
  intro_duration_s double precision,
  intro_transcript text
);
```
- `name` → `users.display_name`; `phone`, `area_name`, `language` already exist on `users`.
- `languages`: the shared `users.spoken_languages` (`0014`) may already cover it: use that one if so, and drop ours.
- Languages: the shared check allows `en, hi, bn, ta, zh, ms`, which covers our four.

### 4.2 Our tables point at `users(id)` (uuid)
- Our 5 migrations have **32** references to `users` (text ids like `u_raj`). Rewrite them as **one new file**
  `0021_bricks_tables.sql` in `public`, every `user_id`-like column `uuid references users(id)`, and drop the
  `bricks` schema files of M1.2 (fresh database, Q9). Table list: circles, circle_members, events, rsvps, checkins,
  reminders, safe_circle, sos_events, sos_responses, walks, skill_offers, endorsements, thanks_skips, user_badges,
  wa_contacts, wa_sessions, wa_seen, messages_log, checkin_runs, event_reminder_sends, reminder_sends, walk_cheers,
  orgs, org_members, health_cards, stories, story_questions.
- Our own ids for other things (`ev_...`, `st_...`) stay text.
- Name clash: our `family_invites` and `family_links` go away (§4.4); nothing else clashes.

### 4.3 Sign-in on our routes
- `core/ctx.py` (`Ctx`): `user_id` comes from the shared `current_user_id` (the shared signed token, 15 min, refreshed by
  the app), not from our Supabase verifier. `auth.py` and `SUPABASE_*` settings removed.
- Our first-sign-in step (create the `users` row from the Supabase token) is gone: the shared `identity` makes the user;
  our side makes the `member_profiles` row on first use of `/v1/me` (or in a hook the shared `identity` calls).
- The shared tokens expire after 15 minutes and answer `401 token_expired`: nothing to do in the backend; M2.2 refreshes.

### 4.4 Family (Q2)
- If Q2 = shared family: "family sees the senior's week" (`family_links.can_view_report`) becomes a **delegation**
  level on the shared `delegations` table; our `parent_overview`, `parent_health_card`, `parent_stories` check that
  delegation instead of `family_links`. Our family invite routes are removed; the app uses the shared ones (M2.2).
- Seniors without email (Q1): the shared **assisted profile** is made by the family member; the senior **claims** it
  later. Our `onboarded_by = 'family'` maps onto that.

### 4.5 Reminders (Q5)
- If Q5 = calendar: our reminder routes become a thin layer over the shared `calendar` service (`kind` medicine /
  exercise / event; `repeat` daily / weekdays / once → its recurrence), so the app's reminder screens keep their API.
  Our WhatsApp reminder sends read calendar occurrences. The shared reminder **calls** take over our call reminders.
- If Q5 = keep ours: only §4.2 applies.

### 4.6 Seed and demo
- `backend/scripts/seed.py` rewritten: users made through the shared `identity` service (real names, as the shared rule
  asks), with emails on a domain we own or assisted profiles; same people and data as today (Raj, Priya, Mdm Tan, ...).
- `/v1/demo/*` (judge accounts, reset) only where Q8 allows it.

### 4.7 Tests
- Our fixtures make users through the shared `identity` and sign requests with its tokens (the shared tests already
  have a helper for that).
