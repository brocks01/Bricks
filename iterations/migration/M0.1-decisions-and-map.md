### 3.1 Answer the open questions

The two projects already built some of the same things. Each row needs one answer.

| # | Question | Options | Suggested |
|---|---|---|---|
| Q1 | **Seniors without email.** The shared `users.email` is required; our seniors can be phone-only or set up by family | (a) Make `email` optional and add `phone` sign-in later · (b) Use the shared **assisted profile + claim** (`0009_claim.sql`) for anyone without email | (b): it already exists for exactly this |
| Q2 | **Family.** Ours: `family_invites`, `family_links` (with `can_view_report`). Shared: `families`, `family_members`, `family_invites`, `delegations` | (a) Shared family module; our "family sees the week" becomes a delegation level · (b) Keep ours, rename our tables | (a): one family model |
| Q3 | **Circles and communities.** Ours: `circles`, `circle_members` (with WhatsApp group links). Shared: `communities`, `memberships`, roles, terms | (a) Circles become communities (kind `interest`), WhatsApp link added · (b) Keep both | (a), if the shared kinds allow small interest groups |
| Q4 | **Events and activities.** Ours: `events`, `rsvps` (places, categories, covers, hosts, check-in). Shared: `activities`, `activity_participants` (inside a community) | (a) Ours become activities, missing fields added · (b) Keep `events`, activities stay for communities | (b) for now: ours carries most of the app; merge later |
| Q5 | **Reminders and the calendar.** Ours: `reminders` (medicine, walk, event; daily/weekdays/once; WhatsApp and call sends). Shared: `calendar_items`, `calendar_marks`, reminder calls with consent | (a) Our reminders become calendar items; the shared reminder-call loop does the calls · (b) Keep ours | (a): the shared calendar already calls people; our voice is being replaced anyway |
| Q6 | **Health.** Ours: `health_cards` (blood group, conditions, medicines, emergency contacts). Shared: `health_readings` (heart rate, sleep, weight, blood pressure) | Different things: keep both | Keep both |
| Q7 | **Which shared modules stay** (no screens in our app yet): communities, explore, grow, calendar, translation, media | Keep all (backend only) · keep some | Keep all: no cost while they have no screens; screens come later |
| Q8 | **Demo data.** The shared rule: "no hard-coded sample data in the app; unbuilt tabs show Coming soon; real names only". Ours: `src/mocks`, `EXPO_PUBLIC_USE_MOCKS`, `seed.py`, the `demo` branch | (a) Mocks only in tests and dev builds, seed only on a demo database · (b) Drop mocks | (a), written into `AGENTS.md` |
| Q9 | **Database host.** Shared: local Postgres 16 + PostGIS, migrations applied at startup. Ours: Supabase Postgres, schema `bricks` | (a) Supabase hosts the shared schema (PostGIS is available) · (b) Another host | (a) for the demo; the `public` schema, fresh start + seed |
| Q10 | **Expo project and app id.** Shared: `com.ankit7129.bricks`, its own EAS project. Ours: `sg.bricks.app` (+ `.dev`, `.preview`), EAS project under `codinsayan` | One of the two | Decide by who builds and shares APKs; the Google Maps key restriction follows the package name |
| Q11 | **Checks in CI.** Shared: app `tsc` + its self-test; backend `pytest`. Ours: app `npm run check` (types, lint with the design-system rules, format, all app tests); backend ruff + mypy + pytest | Add ours · keep shared only | Add ours for the code that moves in |
| Q12 | **Python tooling.** Shared: `requirements.txt` + pip, `python backend/run.py` (port 8800). Ours: uv + `pyproject.toml` | One of the two | The shared one; our dependencies added to `requirements.txt` |
