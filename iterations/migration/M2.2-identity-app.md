# Migration · Iteration M2.2 — One identity: the app

Phase M2 · Est. **5 h** · Source: [M2.1](M2.1-identity-backend.md); shared `modules/identity/router.py` (`/v1/auth/*`, `/v1/me`)

## 1. At a glance

| | |
|---|---|
| **Goal** | The app signs in with an emailed code or Google through the shared `identity`, keeps people signed in with refresh tokens, and no longer uses Supabase |
| **Exit** | Sign in, use the app for 20+ minutes (past one token expiry), sign out, sign in again: no errors; family can set up a senior who claims the account later |

## 2. Entry criteria
- [ ] [M2.1](M2.1-identity-backend.md) done.

## 3. Scope
**In:** sign-in screens (onboarding), the API client's tokens, sign-out, family set-up, the profile.
**Out:** any other screen. Their API stays the same.

## 4. Tasks

### 4.1 Sign-in screens (our look, the shared flow)
- Onboarding sign-in: email → `POST /v1/auth/request-code` → the code screen (6 boxes, our `TextField` style) →
  `POST /v1/auth/verify-code` → tokens. Google: `GET /v1/auth/providers`, then `POST /v1/auth/google` with the Google
  ID token (website on port 3000; on phones the Google sign-in we use today, sending its ID token instead of Supabase's).
- Every word in the four language files (the design-system lint enforces it); built on `<Screen>`.
- Removed: `src/lib/supabase.ts`, the Supabase calls in `features/auth/google.ts` and `onboarding/sign-in.tsx`,
  `EXPO_PUBLIC_SUPABASE_*` (also from the EAS environments), the Supabase packages.

### 4.2 Tokens in the API client (`src/api/client.ts`)
- Keep the access and refresh tokens in secure storage (`expo-secure-store` on phones, `localStorage` on the web).
- On `401` with `token_expired`: **one** `POST /v1/auth/refresh`, then retry the request once; on failure, sign out
  and go to sign-in. Requests waiting at that moment share the one refresh.
- `POST /v1/auth/sign-out` on sign-out.

### 4.3 Profile and onboarding
- `/v1/me` (shared, `display_name`, `language`, ...) plus our profile fields (`member_profiles`, M2.1 §4.1): one call
  or two, matching what M2.1 settled. The app's `Me` type keeps its shape; the client maps the fields.
- Family sets up a senior (Q1): the family flow makes an **assisted profile** (shared `/v1/families/...`), then shares
  the claim link (WhatsApp or QR, as our invites do today); the senior opens it and claims.

### 4.4 Mocks (Q8)
- Mock mode stays only where Q8 allows (tests, dev builds); the mock sign-in returns a mock token in the new shape.

## 8. Risks and fallbacks

| Risk | Fallback |
|---|---|
| Google sign-in on Android needs the shared project's client ids and the app's package name (Q10) | Ship emailed code first; Google after Q10 settles the package name |
| Email delivery of codes is slow on the free mail provider | The shared `EMAIL_PROVIDER` has a console mode for local work; for the demo, pre-made accounts |
